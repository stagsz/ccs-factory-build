# Spec: Decide merge failures by MERGE_HEAD, not git's message

- Job: j-20261015-013
- Branch: factory/j-20261015-013-decide-merge-failures-by-merge-head-not

## Goal
When any factory `git merge` exits non-zero, the orchestrator decides what happened by checking whether `MERGE_HEAD` exists, not by reading git's message. That way a merge that a hook rejects after it started is always aborted, and step 7's record commit can never finish an untested merge.

## Context
- `claude-setup/skills/factory/SKILL.md` has three `git merge` sites, and all of them classify failures by git's message today:
  - Step 5 `local` (line 94): "If the merge reports conflicts ... `git merge --abort` ... `--note "conflicts with <mainBranch>"`" and "If `git merge` exits non-zero without starting a merge ... `--note "merge refused: <git message>"`".
  - `/factory approve` (line 138): "If the merge reports conflicts, run `git merge --abort`, leave the stage as is ..." and "If the merge is refused without starting ... relay git's message".
  - `/factory rework` (line 140): `git -C <worktree> merge --no-edit <mainBranch>` (unquoted). "If the merge reports conflicts, run `git -C <worktree> merge --abort` and tell the user".
- Step 6 (line 110) has a special line 3 for "parked for a merge conflict".
- `tests/skill.test.mjs` pins SKILL.md wording. Line 83 asserts `"exits non-zero without starting a merge"`. Lines 24 and 25 (`git merge --abort`, `do not resolve conflicts yourself`) and line 79 (`merges <mainBranch> into <branch> first`) must keep passing.
- `.claude/` is generated by `npm run setup`. It is not edited.

## Acceptance criteria
- [ ] Step 5 `local` states one rule that applies **whenever `git merge` exits non-zero**: run `git rev-parse -q --verify MERGE_HEAD`.
  - If it succeeds: run `git merge --abort`, then `stage <id> needs-human --note "conflict or rejected merge: <git line>"`, run step 7, then step 6.
  - If it fails: nothing started, so run `stage <id> needs-human --note "merge refused: <git line>"`, run step 7, then step 6.
  - In both cases it says never go on to the tests or `merged`.
- [ ] SKILL.md defines `<git line>` once, in step 5: the first line of git's output that starts with `error:` or `CONFLICT`, with double quotes, `$` and backticks removed. The literal phrase `double quotes, \`$\` and backticks removed` appears. If no such line exists, `<git line>` is the first non-empty line of git's output, cleaned the same way.
- [ ] If `git merge --abort` fails in any of the three sites, SKILL.md says to stop and tell the user and not to run step 7. Contains the substring ``If `git merge --abort` fails, stop and tell the user``.
- [ ] `/factory approve` applies the same `MERGE_HEAD` check, with these differences:
  - It leaves the stage as is in both branches.
  - If `MERGE_HEAD` is set, it aborts and tells the user to use `/factory rework <id> <note>`.
  - If `MERGE_HEAD` is not set, it relays `<git line>`.
  - It never goes on to tests or `merged`.
- [ ] `/factory rework`:
  - Runs `git -C "<worktree>" merge --no-edit <mainBranch>` (quoted).
  - On a non-zero exit, runs `git -C "<worktree>" rev-parse -q --verify MERGE_HEAD`. If that succeeds, it runs `git -C "<worktree>" merge --abort`.
  - In both cases it tells the user `<git line>` and stops. It does not run `board.mjs rework` and does not resume the builder.
  - The text "do not resolve conflicts yourself" remains.
- [ ] The message-based wording is gone: SKILL.md no longer contains `If the merge reports conflicts`, `conflicts with <mainBranch>`, `merge refused: <git message>` or `refused without starting`.
- [ ] Step 6's special line 3 triggers for a job parked as "conflict or rejected merge". The existing line 3 text, including `merges <mainBranch> into <branch> first`, is unchanged.
- [ ] `npm test` passes, and no file outside `claude-setup/skills/factory/SKILL.md` and `tests/skill.test.mjs` changes.

## Risks
- The change touches `claude-setup/**`, an always-escalate path, so the job ends at `needs-human`. That is expected.
- This changes orchestrator behaviour on every merge failure. A wrong rule could let step 7 commit a half-finished merge, which is why the abort-failure stop is required.

## Assumptions
- The request does not say what happens if `git merge --abort` itself fails. In that case `MERGE_HEAD` would survive and step 7's commit would finish the merge, so the spec requires stopping before step 7.
- If git prints no `error:`/`CONFLICT` line, the first non-empty output line is used so the note is never empty.
- Rework does not park, because the job is already `needs-human`. "Tell the user and stop" matches today's behaviour.
- Quoting the rework `git -C "<worktree>" merge --no-edit` command follows the existing quoting rule at line 43. It sits in the sentence being rewritten, so it is in scope.
